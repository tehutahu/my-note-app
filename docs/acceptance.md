# 定量目標と受入テスト v1

すべて**これから達成する目標**。設計時点の達成項目は0件。Aはエージェントの自動検証、Hはユーザーによる実機検証。A/Hの両方が必要な項目は別々に結果を保存する。

## 1. 共通の測定ルール

- 機能テストは乱数seed固定・ローカル合成fixtureで再現可能にする。個人PDFをテストデータにしない。
- Aのブラウザーは固定版Playwright Chromium。最終統合でFirefoxも主要E2Eを実施。実機はTab S7+/S23 UltraのChrome、WindowsのChromeまたはEdge。OS・ブラウザーversionを結果に記録する。
- unitでブラウザーAPIを模擬しても、保存・ポインター・PDF・Service Workerの主要経路は実ブラウザーで検証する。
- 全Aテスト失敗0、必須テストのskip/todo 0。インフラ障害は未実行とし、成功件数へ含めない。
- カバレッジは `src/domain/**` と `src/storage/**` をそれぞれlines/statements/functions 90%以上、branches 85%以上。対象全ファイルを含め、未importファイルを除外して水増ししない。自作入力・PDFアダプターもtests対象とするが、ライブラリ内部は対象外。
- 操作シナリオを最低25本の独立したE2Eでカバーする。単に数を満たすために分割しない。受入IDとテスト名の対応表を `artifacts/acceptance-results.json` に出力する。
- 安定性は最終版の主要E2Eを同じbuildで3回、retry=0で連続実行し全成功。通常のCIも失敗をリトライで隠さない。
- 時間測定は初回warm-up後に10回実行して中央値を採用する。p95が必要な入力測定は1000サンプル以上。生の測定値、端末/コンテナ資源、viewport、build SHAを保存する。
- 性能値はコンテナ上のAと実機Hを分ける。Aの性能基準環境は4 vCPU・8GiB RAM割当、Chromium viewport 1280×800、DPR 1。用意できなければ実際の構成を記録し基準測定は保留。実機Hの機能確認を代用しない。
- CIの共有runner上では性能結果を参考記録とし、専用条件の測定を正式判定に使う。性能以外のA項目はCIで必須にする。

## 5. 保存・障害

| ID | 検証方法 | 合格条件 |
| --- | --- | --- |
| DATA-01 A/H | 200本描画後、保存済みを待ち再読み込み20回 | 座標/筆圧/順序の正規化JSONが毎回一致。Hは3回実施 |
| DATA-02 A | 保存の遅延・失敗・QuotaExceededErrorを注入 | commit前に保存済みを表示しない。失敗時に未保存と再試行を表示、既存commit不変、メモリー上の変更を出力可能 |
| DATA-03 A | 2タブ同時編集、遅い保存順、古いrevisionの保存 | 静かな上書き0。片方は読み取り専用または明示的競合。再取得後最新revision保持 |
| DATA-04 A | schema migration成功/途中失敗、開いた旧タブ、再起動 | 成功時全データ保持、失敗時旧DB保持、閉じるべきタブを案内。DB自動削除0 |

DATA-02のモックだけでは不十分。実IndexedDB transactionを意図的abortするブラウザー試験も含める。電源断やOS強制終了の永続性保証は試験対象外。

## 6. 端末間受け渡し

| ID | 検証方法 | 合格条件 |

| XFER-01 A/H | ノート＋PDF＋3階層をexport→別ストレージへimport→編集→戻す | ID再マップ/日時以外の論理データ一致、添付SHA-256一致。HはAndroid→Windows→Androidで実施 |
| XFER-02 A | 全体バックアップ、ゴミ箱、同じファイル2回取り込み | 階層/削除状態を保持した独立コピー。既存ノート変更0、ID衝突0 |

| XFER-04 A | 取り込みcommitの途中abort、容量不足、commit前キャンセル | 追加レコード0、既存データ変更0。正常取り込みは全レコードを一括可視化 |

専用形式の境界テストは100MiBファイル、64MiB添付合計、200万points、1000ページの許容境界と超過を含める。重い境界試験は専用integration suiteで実行し、日常のunitを不必要に遅くしない。全体バックアップ上限超過はノート単位の書き出しを案内する。

## 9. 性能目標

fixture S：1ページ2000筆跡×100点、図形100個。fixture L：100ノート×10ページ、各ページ100筆跡×50点。fixture P：20ページの合成PDF（文字と画像、合計5MiB以下）。seedと生成方法をリポジトリに保存する。

| ID | 測定方法 | 合格条件 |
| --- | --- | --- |
| PERF-01 A/H | Sを表示し10秒以上筆記。受信イベントhandler開始→次の描画処理終了をperformance.nowで測定、1000サンプル以上 | 処理時間p95≤32ms。イベント処理時間であり物理ペン→画面の総遅延とは表記しない |
| PERF-02 A | Lでノート一覧表示→任意のページ編集可能まで、warm 10回 | 中央値≤1500ms。全ノートの全筆跡を起動時に一括ロードしない |
| PERF-03 A/H | Sに1筆追加して保存開始/commitを計測、10回 | 開始≤300ms（連続入力時≤1秒）、commitまで中央値≤1000ms、失敗表示の漏れ0 |
| PERF-04 A/H | P取り込み・最初のページ表示・全ページPDF出力を各10回 | 取り込み完了中央値≤15秒、warmページ切替≤1500ms、出力≤30秒。処理中は進捗/実行中表示あり |

Aの基準環境とHの各端末を分けて計測する。H性能計測は診断画面からJSONとして書き出せるようにし、ユーザーが開発者ツールを操作しなくても提出できる。端末温度や省電力状態も併記する。数値を満たすために線を無断で間引く、ページを省く、保存完了を早く表示することは禁止。

## 10. リリース判定

| 元の必須要件 | 対応する受入ID |
| --- | --- |
| Androidタブレット・スマートフォンで動く | PWA-01/02、UI-01、INK-06 |
| スタイラスを使える | INK-01〜06、PERF-01 |
| 書く・消す・図形・太さ/モード・背景 | INK-01/04/05、NOTE-03/05 |
| フォルダ階層管理 | NOTE-02/04、XFER-02 |
| Windowsで参照・可能なら編集 | XFER-01、PWA-02、UI-02 |
| PDF出力 | PDF-02/03、PERF-04 |
| PDFを取り込んでノートとして使用 | PDF-01/04/05、PWA-01 |

Hの端末割り当て：入力・筆記品質はAndroid2台それぞれ、共通UI/保存/オフラインはAndroid2台とWindows、端末間受け渡しは各AndroidとWindowsの往復、外部PDFビューアー確認はWindows。Windowsにペン機器の用意は求めない。Aのみの項目をユーザーに手作業で全件再試験させない。

実装完了は全A項目合格、重大なデータ消失/起動不能0件、各機能のレビュー票と再現コマンドあり。H未実施なら「実装済み・実機確認待ち」。日常利用版は必要なHが3端末で完了していること（S Pen項目はAndroid2台）。

未達項目はID・実測・影響・修正予定を残す。閾値変更は測定結果と理由を設計差分として示し、ユーザー承認前に合格へ変えない。
